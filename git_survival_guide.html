Git Survival Guide

A working developer's reference: what each command really does, when to reach for it, and exactly how to get out of trouble. Recovery-first, theory-last.

The 60-second mental model

Almost every confusing Git moment becomes obvious once you know which of four places your change is sitting in, and that a branch is just a sticky note on a commit.

Four places your work can live

PlaceWhat's thereHow things move inHow things move out
Working treeFiles you're editing right nowYou typegit add / git restore
Index (staging)The exact snapshot of your next commitgit addgit restore --staged / git commit
Local repoYour commits & branchesgit commitgit push / git reset
RemoteWhat everyone else seesgit pushgit fetch / git pull
Three facts that resolve 90% of confusion A branch is just a movable pointer to one commit. HEAD is a pointer to the branch you're on. origin/main is not the remote — it's your local cached memory of the remote from the last time you fetched, which is why git status can confidently lie to you until you run git fetch.
The only truly unrecoverable losses Anything committed is recoverable for ~90 days via git reflog. What Git cannot bring back: uncommitted working-tree edits destroyed by git restore, git checkout -- ., or git reset --hard; and untracked files deleted by git clean -fd. Commit or stash before running anything destructive — that's the whole discipline.

Commands · Getting work in

git clone

Copy a remote repository — full history included — onto your machine.

Does
Downloads all objects and history, creates a remote named origin, checks out the default branch, and sets up tracking.
When
Once per project. If you already have the repo, you want git fetch, not another clone.
How
git clone git@github.com:acme/payments-api.git
git clone <url> my-folder          # custom directory name
git clone -b develop <url>         # start on a specific branch
git clone --depth 1 <url>          # shallow: latest commit only, fast CI clone
Example
New laptop, joining a team: clone over SSH so you never fight credential prompts on push.
Mistake
Running git clone while already inside another repository, creating a nested repo that confuses every tool you own.
Don't
Don't git init in a folder you just cloned. Don't embed a token in the clone URL — it gets written to .git/config in plaintext.
Goes wrong
A --depth 1 clone silently breaks git log history, git bisect, and rebasing onto older commits.
Recover
git fetch --unshallow

git status

The command you should run more than any other.

Does
Reports your branch, how it compares to its upstream, what's staged, what's modified, what's untracked — and crucially, whether a merge/rebase/cherry-pick is currently in progress.
When
Before every commit, pull, branch switch, and absolutely before anything with --hard or --force in it.
How
git status
git status -sb   # short + branch line; the daily driver

Reading -sb output: first column = index, second = working tree. M staged modification, M unstaged modification, MM both, ?? untracked, UU conflicted.

Mistake
Skimming past the line "Your branch and 'origin/main' have diverged" and then trying to push.
Goes wrong
Status compares you against a cached origin/main. If you haven't fetched in an hour, "up to date" means nothing.
Recover
git fetch first, then re-read status. Make it a reflex: git fetch && git status -sb.

git add

Choose exactly what goes into the next commit.

Does
Copies the current content of a file into the index. It stages content, not files — edit again after adding and you'll have both a staged and unstaged version.
When
Before committing. Use -p when one file contains two unrelated changes.
How
git add src/auth.js            # one file
git add -p                     # interactive, hunk by hunk — the pro move
git add .                      # everything under current directory
git add -A                     # everything in the repo, incl. deletions
git add -u                     # only already-tracked files
Example
You fixed a bug and also renamed a variable. git add -p lets you ship the fix now and keep the rename for a separate commit.
Mistake
git add . hoovering up .env, node_modules/, a 400 MB fixture, or console.log debris.
Don't
Don't run git add -A from the repo root without reading git status first. Don't fix a bad .gitignore after the fact and expect already-tracked files to disappear — they won't.
Goes wrong
A secret gets staged, then committed, then pushed. Now it's in history and in everyone's clone.
Recover
# staged only
git restore --staged .env

# committed but not pushed
git reset --soft HEAD~1

# tracked by accident, should be ignored from now on
git rm --cached .env && echo ".env" >> .gitignore

# already pushed: ROTATE THE SECRET FIRST, then scrub history
git filter-repo --path .env --invert-paths   # then coordinate a force-push

Treat any pushed secret as compromised. History rewriting is cleanup, not containment.

git commit

Freeze the staged snapshot into permanent, recoverable history.

Does
Creates an immutable object containing the index snapshot, author, message, and a pointer to its parent(s), then moves your branch pointer forward.
When
At every point the code makes sense as a unit. Commit early and often locally — you can always tidy with an interactive rebase before opening the PR.
How
git commit -m "fix(auth): reject expired refresh tokens"
git commit                     # opens editor — use for a real body
git commit -am "msg"           # stage TRACKED changes + commit
git commit --amend             # rewrite the last commit
git commit --amend --no-edit   # same message, add staged changes
Mistake
Believing -am includes new files. It does not — untracked files need an explicit git add.
Don't
Don't --amend a commit that other people have already pulled. Don't write "fix stuff" — future-you will bisect into it and curse.
Goes wrong
You amend a pushed commit; the SHA changes; your next push is rejected as non-fast-forward, and a teammate who pulled the old one now has a divergent history.
Recover
git reflog always still holds the pre-amend commit. If the branch is genuinely yours alone, git push --force-with-lease and tell the team.

Commands · Talking to the remote

git push

Publish local commits to the remote branch.

Does
Uploads commits and fast-forwards the remote branch pointer. It refuses by default if that would discard remote commits.
How
git push
git push -u origin feature/checkout   # first push; sets upstream tracking
git push --force-with-lease           # after rebase/amend, on YOUR branch
git push origin v1.4.0                # push one tag
git push origin --delete old-branch   # delete remote branch

Set this once and never mis-push again:

git config --global push.default simple
git config --global push.autoSetupRemote true
Mistake
Assuming the branch you pushed is the branch you're on. Read the confirmation line Git prints — it names both refs.
Don't
Never git push --force to main, develop, or any branch someone else has checked out. Prefer --force-with-lease universally.
Goes wrong
! [rejected] main -> main (non-fast-forward) — the remote has commits you don't.
Recover
git fetch origin
git rebase origin/main    # or: git merge origin/main
git push

git fetch

The always-safe command. Downloads, changes nothing you can see.

Does
Updates remote-tracking refs (origin/main, origin/feature-x) and downloads objects. Your branch, working tree, and index are untouched.
When
Any time you want the truth about the remote without committing to an integration strategy. There is no scenario where fetching hurts you.
How
git fetch
git fetch --all --prune              # all remotes, drop refs for deleted branches
git fetch origin main

# what landed upstream that I don't have?
git log --oneline HEAD..origin/main
# what do I have that upstream doesn't?
git log --oneline origin/main..HEAD
Mistake
Expecting fetch to update your files. It doesn't — that's the point. Fetch, look, then merge or rebase.
Goes wrong
Your branch list fills with long-dead origin/* branches.
Recover
git fetch --prune, or make it permanent with git config --global fetch.prune true.

git pull

Fetch plus integrate. The command that causes the most accidental merge commits.

Does
git fetch followed by git merge (default) or git rebase (with --rebase) of the upstream branch into yours.
How
git pull --ff-only    # refuse to create a merge; safest default
git pull --rebase     # replay my commits on top of theirs
git pull              # merge — fine on shared branches, noisy on yours
Configure this today 
git config --global pull.ff only
Now git pull either fast-forwards cleanly or stops and tells you to decide. No more surprise "Merge branch 'main' of github.com…" commits.
Mistake
Pulling with a dirty working tree, so the merge aborts halfway or drags your edits into a conflict.
Don't
Don't git pull on a branch you just rebased — plain pull will merge the old remote commits straight back in and duplicate everything.
Goes wrong
You end up with a tangled merge or your rebase undone.
Recover
git reset --hard ORIG_HEAD   # ORIG_HEAD = where you were before the pull
Works immediately after the pull. Later, use git reflog.

git remote

Manage the URLs Git talks to.

How
git remote -v
git remote add upstream git@github.com:original/repo.git   # fork workflow
git remote set-url origin git@github.com:acme/repo.git     # HTTPS → SSH
git remote show origin                                     # incl. stale branches
git remote prune origin
Example
Working on a fork: origin is yours, upstream is the source. Sync with git fetch upstream && git rebase upstream/main.
Mistake
Pushing to upstream instead of origin on a fork you don't own.
Recover
Ask a maintainer to revert, or if you have rights: git push upstream --force-with-lease <branch>:<branch> back to the previous SHA from your reflog.

Commands · Branching & moving around

git branch

List, create, rename, and delete pointers.

How
git branch -vv                # local branches + upstream + ahead/behind
git branch -a                 # include remote-tracking branches
git branch feature/x abc1234  # create at a specific commit (recovery!)
git branch -m new-name        # rename current branch
git branch -d old             # safe delete: refuses if unmerged
git branch -D old             # force delete
git branch --merged main      # what's safe to clean up

Bulk cleanup of branches already merged into main:

git branch --merged main | grep -vE "^\*|main|develop" | xargs -r git branch -d
Mistake
Reaching for -D the moment -d complains. That complaint is the safety net doing its job.
Goes wrong
You -D a branch holding two days of unmerged work.
Recover
git reflog                        # find the branch tip SHA
git branch feature/x abc1234      # resurrect it

git switch

The modern, unambiguous way to change branches (Git 2.23+). Prefer it over checkout.

How
git switch main
git switch -c feature/checkout        # create + switch
git switch -                          # back to previous branch
git switch -c fix origin/fix          # start from a remote branch
git switch --detach abc1234           # deliberately detached HEAD
Why
checkout does two unrelated jobs — moving HEAD and overwriting files — so a typo can silently destroy work. switch only moves HEAD and refuses when it would lose changes.
Goes wrong
"Your local changes would be overwritten by checkout."
Recover
Pick one: commit them, git stash -u them, or carry them across with git switch -m other-branch.

git checkout

The legacy Swiss-army knife. Still everywhere in docs and muscle memory.

Does
Three different jobs depending on arguments: switch branches, detach HEAD onto a commit, or overwrite files from a commit.
How
git checkout main                  # → git switch main
git checkout -b feature/x          # → git switch -c feature/x
git checkout abc1234               # → git switch --detach abc1234
git checkout -- src/app.js         # → git restore src/app.js  ⚠ DESTRUCTIVE
git checkout main -- config.yml    # take one file from another branch
Don't
git checkout -- . is the single most common way developers permanently lose an afternoon of work. There is no reflog for uncommitted files.
Recover
If the content was ever git add-ed, the blob still exists: git fsck --lost-found, then read the dangling blobs. Otherwise, your editor's local history is the only hope.

Commands · Integrating work

git merge

Join two histories, preserving what actually happened.

Does
Fast-forwards the pointer if possible; otherwise creates a merge commit with two parents. Existing commits are never rewritten.
When
Bringing a finished feature into a shared branch, or updating your branch from main when others share it.
How
git switch main && git merge feature/checkout
git merge --no-ff feature/x     # always record a merge commit
git merge --squash feature/x    # collapse into one staged change
git merge --abort               # bail out mid-conflict
Mistake
Committing a conflict resolution that still contains <<<<<<< markers, or resolving by deleting the other person's code wholesale.
Don't
Don't merge main into your feature branch ten times — the log becomes unreadable. Rebase, or merge once at the end.
Goes wrong
A bad merge lands and breaks the build.
Recover
git merge --abort                    # still mid-merge
git reset --hard ORIG_HEAD           # merged locally, not pushed
git revert -m 1 <merge-sha>          # already pushed (-m 1 = keep the branch you merged INTO)

git rebase

Replay your commits on a new base. New SHAs, linear history, sharper edges.

Does
Takes each of your commits, re-applies them one at a time on top of the target, producing brand-new commits. The originals become unreferenced (but live on in reflog).
When
Tidying your own unpushed branch before review, or updating a solo feature branch onto the latest main.
How
git fetch && git rebase origin/main
git rebase -i HEAD~4          # squash / reword / reorder / drop
git rebase --continue         # after resolving a conflict
git rebase --skip             # drop the commit being applied
git rebase --abort            # full undo, back to the start
git rebase --autostash origin/main   # auto-shelve dirty tree first

In interactive mode: pick keep · reword change message · squash fold into previous keeping both messages · fixup fold in silently · edit pause to amend · drop delete.

Don't
The golden rule: never rebase commits that exist on a branch other people have pulled. You're not editing history, you're handing everyone a different history.
Goes wrong
Conflicts fire on every single commit; you lose track of which step you're on; the finished branch needs a force-push.
Recover
git rebase --abort                       # mid-rebase: nothing lost
git reflog                               # finished but wrong
git reset --hard HEAD@{5}                # the SHA from just before the rebase

Turn on conflict memory so you only solve each conflict once: git config --global rerere.enabled true.

git cherry-pick

Copy one specific commit onto the branch you're on.

Does
Re-applies a commit's diff as a new commit with a new SHA on your current branch.
When
Backporting a hotfix to a release branch, or rescuing a commit you made on the wrong branch.
How
git cherry-pick abc1234
git cherry-pick abc1234 def5678       # several
git cherry-pick abc1234..def5678      # a range (exclusive of the first)
git cherry-pick -n abc1234            # apply but don't commit
git cherry-pick -x abc1234            # record source SHA in the message
git cherry-pick --continue | --abort
Example
Critical fix is on main, customers are on release/2.3. git switch release/2.3 && git cherry-pick -x <sha>.
Mistake
Cherry-picking instead of merging a whole branch — you get duplicate commits with different SHAs and confusing conflicts when the branch merges later.
Recover
git cherry-pick --abort mid-flight; git reset --hard HEAD~1 if it's committed and unpushed; git revert if pushed.

Commands · Undoing & shelving

git reset

Move the branch pointer. The mode decides how much collateral damage.

Does
ModeBranch ptrIndexWorking treeUse it to…
--softmoveskeptkeptredo the last commit, changes stay staged
--mixed (default)movesresetkeptunstage everything, keep edits
--hardmovesresetwipedthrow it all away
How
git reset --soft HEAD~1        # undo last commit, keep everything staged
git reset HEAD~1               # undo last commit, keep files, unstage
git reset --hard origin/main   # make local identical to remote ⚠
git reset --hard ORIG_HEAD     # undo the merge/rebase/pull I just did
Don't
Never --hard with uncommitted work you'd miss, and never on a pushed shared branch — use git revert there instead.
Recover
Discarded commits are safe: git reflog → git reset --hard HEAD@{1}. Discarded uncommitted changes are gone unless they were staged, in which case try git fsck --lost-found.

git revert

Undo by adding, not deleting. The only safe undo for pushed work.

Does
Creates a new commit applying the inverse diff. History stays intact, so nobody else's clone breaks.
When
Anything already on main, or any branch someone else might have.
How
git revert abc1234
git revert --no-commit abc1234 def5678   # batch into one commit
git revert -m 1 <merge-sha>              # revert a merge commit
Mistake
Reverting a merge, then later re-merging the same branch and wondering why the changes don't come back — Git thinks it's already merged.
Recover
Revert the revert (git revert <revert-sha>), or rebase the feature branch onto the new main so its commits get fresh SHAs.

git restore

Modern, explicit file-level undo (Git 2.23+). Replaces checkout -- and reset HEAD.

How
git restore src/app.js                     # discard unstaged edits ⚠ permanent
git restore --staged src/app.js            # unstage, keep the edit
git restore --staged --worktree src/app.js # nuke both
git restore --source=HEAD~2 -- config.yml  # pull one file from an old commit
git restore .                              # discard ALL unstaged edits ⚠⚠
Don't
Don't type git restore . as a "reset my mess" reflex. Run git stash -u instead — same clean tree, fully reversible.
Recover
Unstaged content is unrecoverable. Staged content may survive in dangling blobs: git fsck --lost-found.

git stash

Shelve work-in-progress and get a clean tree in one move.

Does
Saves modified tracked files (untracked only with -u) onto a stack of hidden commits, then reverts the working tree.
How
git stash push -u -m "wip: checkout validation"
git stash list
git stash show -p stash@{0}     # inspect before applying
git stash pop                   # apply + delete entry
git stash apply stash@{1}       # apply, keep entry (safer)
git stash branch fix-wip        # new branch from the stash's base commit
git stash drop stash@{0}
Mistake
Forgetting -u, so brand-new files stay behind — and then git clean -fd deletes them. Also: unlabelled stashes pile up until nobody knows what stash@{4} was.
Don't
Don't use stash as long-term storage. A WIP commit on a scratch branch is visible, named, and safe.
Goes wrong
git stash pop conflicts. Note the entry is kept when pop conflicts — don't panic and re-pop.
Recover
# dropped or cleared a stash by accident
git fsck --unreachable | grep commit | cut -d' ' -f3 | xargs git log --merges --no-walk --oneline
git stash apply <sha>

Commands · Looking around

git log

Read history — and answer "who broke this and when".

How
git log --oneline --graph --decorate --all   # the one to alias
git log -5 --stat
git log -p src/auth.js            # full diffs for one file
git log --follow src/auth.js      # survive renames
git log -S"deprecatedFlag"        # pickaxe: when was this string added/removed
git log --author="priya" --since="2 weeks ago"
git log main..feature             # in feature, not in main
git log --oneline HEAD..origin/main   # what I'm about to pull

Worth aliasing: git config --global alias.lg "log --oneline --graph --decorate --all -20"

Mistake
Confusing A..B (commits in B not in A) with A...B (commits in either but not both). For git diff the three-dot form means "changes on B since it diverged from A" — that's the PR view.

git diff

See exactly what changed, before you commit something you regret.

How
git diff                      # working tree vs index (unstaged)
git diff --staged             # index vs HEAD — what you're about to commit
git diff HEAD                 # everything uncommitted
git diff main...feature       # what the PR will show
git diff --stat               # summary only
git diff --name-only main     # just the file list
git diff abc1234 def5678 -- src/
Mistake
Running plain git diff after staging, seeing nothing, and concluding there are no changes. You want --staged.

git show

Inspect one object in detail.

How
git show abc1234                  # message + full diff
git show abc1234 --stat           # files touched only
git show abc1234:src/config.js    # file contents AT that commit
git show HEAD~3
git show v1.4.0                   # what a tag points at
Example
Before cherry-picking, git show <sha> to confirm it's really the fix and doesn't drag unrelated changes along.

git tag

Name a commit permanently — usually a release.

How
git tag -a v1.4.0 -m "Release 1.4.0"   # annotated: use this for releases
git tag v1.4.0-rc1                     # lightweight: just a pointer
git push origin v1.4.0
git push --tags                        # push all local tags
git tag -d v1.4.0                      # delete locally
git push origin --delete v1.4.0        # delete on remote
git describe --tags                    # human-readable version of HEAD
Mistake
Assuming git push sends tags. It doesn't — tags need an explicit push, which is why CI so often fails to see a release.
Don't
Don't move a published tag. Anyone who already fetched keeps the old one, and now "v1.4.0" means two different things. Cut v1.4.1 instead.

Commands · Power tools

git clean

Delete untracked files. Irreversible. Always dry-run first.

How
git clean -n           # DRY RUN — always start here
git clean -nd          # incl. untracked directories
git clean -fd          # actually delete
git clean -fdx         # also delete ignored files (node_modules, .env) ⚠⚠
git clean -i           # interactive
Don't
-fdx deletes your .env, local certs, and IDE settings. There is no reflog, no stash, no undo.
Recover
Nothing in Git can help. Only your OS trash, backup, or IDE local history. This is why -n exists.

git bisect

Binary-search history to find the commit that introduced a bug. 1000 commits → 10 tests.

How
git bisect start
git bisect bad                 # current commit is broken
git bisect good v1.3.0         # this release was fine
# Git checks out a midpoint; test it, then:
git bisect good   |   git bisect bad
# ...repeat until Git names the first bad commit
git bisect reset               # ALWAYS finish with this

# fully automated:
git bisect run npm test -- tests/checkout.spec.js
Mistake
Forgetting git bisect reset, leaving yourself in detached HEAD hours later wondering where your branch went.
Recover
git bisect reset returns you to the branch you started from. Use git bisect skip for commits that don't build.

git reflog

The undo history for your branch pointers. This is the command that saves your job.

Does
Logs every position HEAD has occupied — commits, checkouts, resets, merges, rebases — even if the commits are no longer reachable from any branch. Kept ~90 days.
When
The instant you think "my work is gone". Before you try anything else.
How
git reflog
git reflog --date=relative
git reflog show feature/x           # one branch's history
git show HEAD@{3}                   # inspect before jumping

# two ways back:
git reset --hard HEAD@{3}           # move current branch there
git branch rescue abc1234           # or park it on a new branch (safer)
Golden rule
Recover onto a new branch first (git branch rescue <sha>), inspect it, and only then reset. That way a mis-read reflog entry costs you nothing.
Limits
Reflog is local and per-clone — it can't recover someone else's lost work, it doesn't cover uncommitted changes, and entries expire (30 days for unreachable commits, 90 for the rest).

Workflow · Feature branch, start to finish

# 1. Start from a genuinely current main
git switch main
git pull --ff-only

# 2. Branch
git switch -c feat/checkout-validation

# 3. Work in small commits
git add -p
git commit -m "feat(checkout): validate postal codes"

# 4. Publish early — a pushed branch is a backup
git push -u origin feat/checkout-validation

# 5. Stay current while you work (solo branch → rebase)
git fetch origin
git rebase origin/main
git push --force-with-lease

# 6. Tidy the story before review
git rebase -i origin/main      # squash "fix typo" commits away
git push --force-with-lease

# 7. Open PR, get it merged, then clean up
git switch main && git pull --ff-only
git branch -d feat/checkout-validation
git fetch --prune
The one rule that keeps this safe Rebase and force-push freely on a branch only you have. The moment a second person checks it out, switch to git merge origin/main and stop force-pushing.

Workflow · Pulling latest changes without drama

# The safe sequence, every time
git status                   # dirty? commit or stash first
git stash push -u -m "wip"   # if dirty
git fetch origin
git log --oneline HEAD..origin/main    # see what's coming
git pull --ff-only           # or: git rebase origin/main
git stash pop                # if you stashed
What --ff-only tells youMeaningDo this
Fast-forwards cleanlyYou had no local commitsNothing — you're done
fatal: Not possible to fast-forwardYou have local commits too; histories divergedgit rebase origin/main (your branch) or git merge origin/main (shared)

Workflow · Merge vs rebase, decided in ten seconds

QuestionAnswer → do this
Has anyone else pulled this branch?Yes → merge. No → rebase is fine
Are you updating your own feature branch from main?Rebase — linear history, clean PR diff
Are you bringing a finished feature into main?Merge (often squash-merge via the PR button)
Is this main, develop, or release/*?Never rebase. Merge or revert only
Do you need to preserve the true sequence of events (audit, incident)?Merge — rebase invents a history that never happened
Deep in conflicts and losing the thread?Merge — one conflict resolution instead of one per commit
Trade-off in one line Merge keeps history honest but bushy; rebase keeps it readable but rewrites SHAs, which means force-pushing, which means it must be your branch alone.

Workflow · Resolving merge conflicts

Steps
  1. git status — the "Unmerged paths" list is your to-do list.
  2. Open each file and find the markers.
  3. Edit to the correct combined result and delete all three marker lines.
  4. git add <file> to mark it resolved.
  5. Repeat, then git commit (merge) or git rebase --continue (rebase).
  6. Run the tests. A conflict that compiles is not a conflict that's correct.
Markers
<<<<<<< HEAD
const timeout = 3000;        // "ours"
=======
const timeout = 5000;        // "theirs"
>>>>>>> feature/slow-network
Shortcuts
git checkout --ours  path/to/file    # take one side wholesale
git checkout --theirs path/to/file
git diff --name-only --diff-filter=U # list conflicted files
git mergetool                        # open your configured 3-way tool
git merge --abort  |  git rebase --abort
Gotcha
During a rebase, "ours" and "theirs" are swapped. "Ours" is the branch you're rebasing onto (e.g. main) and "theirs" is your commit being replayed. Check with git status before blindly picking a side.
Don't
Don't resolve by deleting the other person's code to make the error go away. Don't commit with markers still in the file — grep for <<<<<<< before committing.
Prevention
Small PRs, short-lived branches, rebase onto main daily, and git config --global rerere.enabled true so Git replays resolutions you've already made.

Workflow · Undoing commits — the decision matrix

SituationCommandResult
Last commit, message wronggit commit --amendRewrites it in place
Last commit, forgot a filegit add f && git commit --amend --no-editFolds it in
Undo last commit, keep changes stagedgit reset --soft HEAD~1Ready to re-commit
Undo last commit, keep files onlygit reset HEAD~1Unstaged edits remain
Undo last commit and the workgit reset --hard HEAD~1Gone (reflog only)
Undo last 3 commits, keep the codegit reset --soft HEAD~3One clean re-commit
Undo a commit from the middlegit rebase -i <sha>~1 → dropRewrites history after it
Already pushed / sharedgit revert <sha>New inverse commit — safe
The dividing line Not pushed → reset and amend are free. Pushed and shared → revert. The only exception is a personal feature branch, where --force-with-lease is acceptable if you announce it.

Workflow · Keeping local and remote in sync

# Morning routine
git fetch --all --prune
git switch main && git pull --ff-only
git branch -vv                       # see ahead/behind + [gone] branches

# Clean up branches whose remote was deleted after merge
git fetch --prune

The panic room · Real situations, safe fixes

Each entry follows the same shape: what happened → why → what not to do → the safe fix → prevention. Find yours with the search box above.

"I committed on main by mistake." (not pushed)

Happened
Two commits are sitting on local main that belong on a feature branch.
Why
You started coding before switching branches — the classic "just a quick fix" trap.
Don't
Don't git reset --hard first and hope the code survives. Don't push "just to be safe".
Safe fix
Create the branch from where you are (it keeps the commits), then rewind main.
Commands
git branch feature/my-work       # branch now points at your commits
git reset --hard origin/main     # main back to the remote's position
git switch feature/my-work       # carry on working

# Only some commits belong elsewhere? cherry-pick instead:
git switch -c feature/my-work
git cherry-pick abc1234
git switch main && git reset --hard origin/main
Prevention
Put the branch name in your shell prompt, and enable branch protection on main so a stray push is refused by the server.

"I accidentally pushed to the wrong branch."

Happened
Commits meant for a feature branch are now on main (or another shared branch) on the remote.
Why
Wrong upstream tracking, or you never switched branches.
Don't
Don't force-push main back to its old SHA if anyone may have pulled. You'd be rewriting shared history and everyone who pulled gets a broken clone.
Safe fix
Copy the commits where they belong, then revert them on the shared branch.
Commands
# 1. Get the work onto the right branch
git switch -c feature/correct origin/main~2   # base before your commits
git cherry-pick abc1234 def5678
git push -u origin feature/correct

# 2. Undo them on main, safely
git switch main && git pull --ff-only
git revert def5678 abc1234        # newest first
git push

If you pushed within seconds, it's a private branch, and you've confirmed with the team, git push --force-with-lease origin main back to the old SHA is acceptable — announce it either way.

Prevention
Branch protection rules, plus git config --global push.default simple so you never push a branch you're not on.

"I pulled and now Git says the branches have diverged."

Happened
"Your branch and 'origin/main' have diverged, and have 2 and 5 different commits each."
Why
You committed locally while someone else pushed. Both histories moved forward from a shared ancestor — normal, not broken.
Don't
Don't git reset --hard origin/main — that silently deletes your 2 commits. Don't force-push over their 5.
Safe fix
Look first, then pick rebase (your branch) or merge (shared branch).
Commands
git fetch origin
git log --oneline --graph --all -15
git log --oneline origin/main..HEAD    # MY commits — confirm they matter

# Your own feature branch → replay on top, stay linear
git rebase origin/main
git push --force-with-lease

# Shared branch → merge, no force-push needed
git merge origin/main
git push
Prevention
git pull --ff-only as your default — it refuses to guess and hands you the decision before anything happens.

"I'm in the middle of a rebase and don't know what to do."

Happened
Prompt shows something like (feature|REBASE 3/7), there are conflicts, and every command feels risky.
Why
Git is replaying your commits one at a time and stopped on commit 3 of 7 because it couldn't apply it cleanly.
Don't
Don't git commit (use --continue), don't git pull, don't switch branches, and don't delete .git/rebase-merge/ by hand.
Safe fix
When in doubt: git rebase --abort. It returns you exactly to where you started, losing nothing. There is no shame in aborting.
Commands
git status                  # tells you which step and which files

# A) Get out, no harm done
git rebase --abort

# B) Push through
git diff --name-only --diff-filter=U   # conflicted files
# ...edit each one, remove markers...
git add <file>
git rebase --continue

# C) This commit is now redundant (already upstream)
git rebase --skip

Remember: during rebase, --ours = the branch you're rebasing onto, --theirs = your own commit.

Prevention
Rebase onto main daily so you resolve one small conflict instead of twenty. Enable rerere.

"I accidentally force-pushed."

Happened
You overwrote the remote branch and someone else's commits are no longer there.
Why
--force tells the remote "make the branch this, regardless of what's there".
Don't
Don't force-push again to "fix" it before you know the correct target SHA. Don't stay quiet — tell the team immediately so nobody else pulls the damaged branch.
Safe fix
Find the old remote SHA and force-push it back. Sources, in order of ease: your own git reflog; a teammate's clone (git reflog show origin/main); GitHub/GitLab's activity or events API, which records the "before" SHA of every push; or a CI job log.
Commands
git reflog show origin/main         # your cached view of the remote
git log --oneline <old-sha> -5      # verify it's the right history
git push --force-with-lease origin <old-sha>:main

# A teammate who still has the good commits can simply:
git push origin main
Prevention
Alias force away: git config --global alias.pushf "push --force-with-lease" and never type --force. Enable branch protection so the server rejects force-pushes to main outright.

"--force vs --force-with-lease: which do I use?"

Difference
--force overwrites the remote unconditionally. --force-with-lease first checks the remote branch still points where you last saw it, and aborts if someone pushed in the meantime.
Rule
Use --force-with-lease. Always. There is no situation where plain --force is meaningfully better.
Sharp edge
The "lease" is based on your remote-tracking ref. If your IDE auto-fetches in the background, the ref silently updates and the lease now approves the overwrite. Pin it explicitly when it matters:
Commands
git push --force-with-lease
git push --force-with-lease=main:<sha-I-expect-on-remote>   # bulletproof

"My commit disappeared."

Happened
Work you know you committed isn't in git log anymore.
Why
Almost always one of: a reset --hard, a rebase that dropped or squashed it, a deleted branch, an amend that replaced it, or you're on a different branch than you think.
Don't
Don't run git gc, don't re-clone, and don't keep running destructive commands — every one of them adds noise to the reflog you're about to read.
Safe fix
Committed work is essentially never lost for ~90 days. Find the SHA, park it on a new branch, verify, then merge.
Commands
git reflog --date=relative | head -30
git show HEAD@{5}                    # is this the one?
git branch rescue HEAD@{5}           # park it safely — don't reset yet
git switch rescue && git log --oneline -5

# Reflog doesn't have it (e.g. commit made in a deleted branch)
git fsck --lost-found
git log --oneline --all --grep="part of the message"
Prevention
Push feature branches early — a pushed branch is an off-machine backup that no local mistake can touch.

"I have merge conflicts."

Happened
"Automatic merge failed; fix conflicts and then commit the result."
Why
Two branches changed the same lines, or one edited a file the other deleted. Git refuses to guess.
Don't
Don't commit with markers still in the file. Don't blindly --theirs everything to make it stop. Don't leave a half-resolved merge overnight — git stash won't save you cleanly from it.
Safe fix
Resolve file by file, stage each as you go, run the tests, then complete the operation.
Commands
git status                                # the to-do list
git diff --name-only --diff-filter=U
# edit files, delete <<<<<<< ======= >>>>>>>
git add <file>
git commit                                # merge
git rebase --continue                     # rebase

# escape hatch
git merge --abort   |   git rebase --abort
Prevention
Smaller, shorter-lived branches; sync with main daily; agree on formatting/lint config so the whole team isn't reformatting the same lines.

"I need to undo a commit that is already pushed."

Happened
A bad commit is on a shared branch and other people have it.
Why
It happens. The question is only whether you undo it safely or make it everyone's problem.
Don't
Don't reset --hard + force-push a shared branch. Everyone who pulled will re-push the "missing" commits and it comes straight back, tangled.
Safe fix
git revert. It's a normal forward commit — reviewable, revertible, and it breaks nobody's clone.
Commands
git switch main && git pull --ff-only
git revert abc1234
git push

# several commits — newest first
git revert --no-commit def5678 abc1234
git commit -m "revert: roll back broken checkout validation"

# it was a merge commit
git revert -m 1 <merge-sha>
Prevention
Require PR review and green CI before merge to main.

"I have uncommitted changes and need to switch branches."

Happened
"Your local changes would be overwritten by checkout."
Why
The target branch has different content in files you've edited, so switching would destroy your edits. Git is protecting you.
Don't
Don't reach for git checkout -f or git restore . to "clear the block" — that's exactly the data loss Git just prevented.
Safe fix
Three good options depending on whether the work belongs here or there.
Commands
# A) Work belongs on THIS branch → commit (even as WIP)
git add -A && git commit -m "wip"

# B) Shelve it, switch, come back later
git stash push -u -m "wip: cart totals"
git switch other-branch
# ...later...
git switch -  &&  git stash pop

# C) Work belongs on the OTHER branch → carry it across
git switch -m other-branch      # merges your edits into the switch

# D) Genuinely don't need it
git restore .                   # ⚠ permanent
Prevention
Set git config --global rebase.autostash true, and use git worktree add ../hotfix main when you need two branches checked out at once instead of context-switching.

"My stash is gone / stash pop hit a conflict."

Happened
You dropped a stash, ran git stash clear, or pop conflicted and you're unsure what state you're in.
Why
pop = apply + drop, but on conflict it keeps the entry. clear deletes every entry with no confirmation.
Don't
Don't re-run git stash pop repeatedly during a conflict — you'll stack duplicate changes. Don't git reset --hard to escape; that discards the applied part too.
Safe fix
Stash entries are commits, so git fsck can find them even after a drop.
Commands
# pop conflicted: resolve like any conflict, then remove the entry
git status && git add <resolved-files>
git stash drop

# dropped/cleared by accident — find orphaned stash commits
git fsck --unreachable | grep commit | cut -d' ' -f3 \
  | xargs git log --merges --no-walk --oneline
git stash apply <sha>
Prevention
Prefer git stash apply over pop (keeps the safety copy), always label with -m, always include -u, and don't let stashes live more than a day.

"I'm in detached HEAD state."

Happened
"You are in 'detached HEAD' state." Commits you make here belong to no branch.
Why
You checked out a raw SHA or tag, or you're mid-bisect/mid-rebase. HEAD points at a commit instead of a branch.
Don't
Don't git switch main if you've made commits here — they become unreferenced immediately (recoverable via reflog, but why).
Safe fix
If you made commits, give them a branch first. If you didn't, just switch away.
Commands
# Made commits you want to keep
git switch -c rescue-work        # names your current position
git switch main && git merge rescue-work

# Made nothing / don't care
git switch main

# Already left and lost them
git reflog && git branch rescue <sha>

# It was bisect
git bisect reset
Prevention
Use git switch --detach <sha> when you mean it, and create a branch the moment you decide to commit.

"I accidentally deleted a branch."

Happened
git branch -D feature/x and it had unmerged commits.
Why
-D skips the merge-safety check that -d performs.
Don't
Don't run git gc --prune=now — that's the one thing that can actually make it permanent.
Safe fix
The commits still exist; only the pointer was removed. Recreate the pointer.
Commands
git reflog                        # find last commit on that branch
git branch feature/x abc1234      # resurrect

# It was pushed once — even easier
git fetch origin
git switch -c feature/x origin/feature/x

# Reflog too noisy
git fsck --full --no-reflogs --unreachable --lost-found
git log --oneline --all --grep="known commit text"
Prevention
Use -d and let it refuse. Push branches so the remote holds a copy.

"My commit message is wrong."

Happened
Typo, wrong ticket number, or a message that says nothing.
Why
-m with fingers faster than brain.
Don't
Don't amend or rebase a message on a shared branch just for tidiness — rewriting public history to fix a typo isn't worth the disruption. Add a follow-up note in the PR instead.
Safe fix
Amend if it's the last commit; interactive rebase with reword if it's older; both are fine while unpushed or on a solo branch.
Commands
git commit --amend -m "fix(api): handle null customer id"   # last commit

git rebase -i HEAD~5      # older: change 'pick' → 'reword' on that line

# if it was already pushed to YOUR OWN branch
git push --force-with-lease
Prevention
Use git commit without -m so the editor opens, and add a commit-message template with git config --global commit.template ~/.gitmessage.

"I need to remove a file from a commit."

Happened
A .env, a 200 MB binary, or someone else's unrelated change rode along.
Why
git add . without reading git status.
Don't
Don't just delete the file in a new commit and call it done — it's still in history, still in every clone, and still fetchable. For secrets that's a breach, not a typo.
Safe fix
Depends entirely on whether it's pushed.
Commands
# Last commit, not pushed
git rm --cached .env
git commit --amend --no-edit
echo ".env" >> .gitignore

# Older commit, not pushed
git rebase -i <sha>~1      # mark 'edit'
git rm --cached path/to/file
git commit --amend --no-edit
git rebase --continue

# Already pushed — rewrite history (coordinate with the team!)
git filter-repo --path path/to/file --invert-paths
git push --force-with-lease --all
If it was a credential Rotate the key first. History rewriting takes hours and never reaches forks, caches, or CI logs. Assume it's compromised the moment it's pushed.
Prevention
A good .gitignore from day one, plus a pre-commit secret scanner (gitleaks, git-secrets).

"I ran git reset --hard and lost work."

Happened
Commits and/or uncommitted edits vanished.
Why
--hard moves the branch pointer and overwrites the index and working tree.
Don't
Don't keep running commands hoping something reappears. Don't git gc. Stop and read the reflog.
Safe fix
Committed work: fully recoverable. Staged-but-uncommitted: usually recoverable as dangling blobs. Never-staged edits: gone — check your editor's local history.
Commands
git reflog
git branch rescue HEAD@{1}        # park it, verify, then merge

# it was staged but never committed
git fsck --lost-found
ls .git/lost-found/other/          # dangling blobs; cat them to identify
Prevention
Make git stash -u your "clean slate" reflex instead of reset --hard. It gives the same clean tree and is fully reversible.

"A bad merge or rebase landed and I want it gone."

Happened
The merge/rebase completed but the result is wrong — duplicated commits, lost changes, broken build.
Why
Conflicts resolved in the wrong direction, or the wrong base was chosen.
Don't
Don't try to hand-patch the result forward. Rewind to a known-good SHA and redo it deliberately.
Safe fix
Not pushed → reset to ORIG_HEAD or a reflog SHA. Pushed → revert the merge commit.
Commands
# Immediately after, not pushed
git reset --hard ORIG_HEAD

# A while later, not pushed
git reflog
git reset --hard HEAD@{7}         # the entry just before the operation

# Already pushed to a shared branch
git revert -m 1 <merge-sha>       # -m 1 keeps the branch you merged INTO
git push

If you later need to re-merge that feature after reverting the merge, revert the revert first — otherwise Git considers it already merged and brings nothing.

Prevention
Tag or note the SHA before risky operations: git branch backup-$(date +%F) costs one second.

"Push rejected: non-fast-forward."

Happened
! [rejected] main -> main (fetch first) or (non-fast-forward).
Why
The remote branch has commits you don't have locally, so your push would erase them. Git refuses.
Don't
Don't "solve" it with --force. That does exactly what Git just stopped: deletes your colleague's work.
Safe fix
Integrate the remote commits first, then push normally.
Commands
git fetch origin
git log --oneline HEAD..origin/main    # what am I missing?

git rebase origin/main                 # your branch → linear
# or
git merge origin/main                  # shared branch → safe

git push

The one legitimate exception: you rebased or amended your own feature branch. Then git push --force-with-lease is correct and expected.

Prevention
Fetch before you push. git pull --ff-only && git push as one habit.

5 · Short interview questions

Click to reveal a crisp answer. These are the ones that actually come up.

What's the difference between git fetch and git pull?
Fetch downloads remote objects and updates remote-tracking refs, changing nothing in your working tree. Pull is fetch plus an immediate merge or rebase into your current branch. Fetch is always safe; pull makes a decision for you.
Merge vs rebase?
Merge joins two histories with a merge commit and never rewrites existing commits — honest but bushy. Rebase replays your commits onto a new base, creating new SHAs — linear and readable, but it rewrites history, so only on branches nobody else has.
What are reset, revert, and restore for?
reset moves a branch pointer (and optionally index/working tree) — for local, unpushed history. revert creates a new commit that undoes an old one — for pushed, shared history. restore operates on files in the working tree or index, not on commits.
Explain --soft, --mixed, and --hard.
All three move the branch pointer. --soft leaves index and working tree intact (changes stay staged). --mixed (default) resets the index but keeps the working tree (changes remain, unstaged). --hard resets everything, discarding uncommitted work permanently.
What is HEAD, and what is a detached HEAD?
HEAD is a pointer to your current branch, which in turn points to a commit. Detached HEAD means HEAD points straight at a commit with no branch in between, so new commits belong to nothing and become unreachable when you switch away — recoverable via reflog, or preventable with git switch -c <name>.
--force vs --force-with-lease?
--force overwrites the remote branch unconditionally. --force-with-lease verifies the remote still points where your last fetch saw it and aborts otherwise, protecting commits pushed by others in the meantime. Always prefer the lease version.
Golden rule of rebasing?
Never rebase commits that have been pushed to a branch other people work on. Rebase produces new SHAs, so everyone else's history instantly diverges from yours.
How do you undo a commit that's already pushed?
git revert <sha> then push. It adds an inverse commit rather than rewriting history, so no one's clone breaks. For a merge commit, git revert -m 1 <sha>.
What is git reflog and when do you use it?
A local log of every position HEAD has held — including commits no branch points to anymore. It's the recovery tool for bad resets, botched rebases, deleted branches, and lost commits, typically covering the last ~90 days.
How do you recover a deleted branch?
Find the branch tip in git reflog, then git branch <name> <sha>. If it had been pushed, simpler still: git switch -c <name> origin/<name>.
What is the index / staging area for?
It's the proposed snapshot of your next commit. It lets you commit a curated subset of your changes — for example splitting one messy working tree into two clean, reviewable commits with git add -p.
Cherry-pick vs merge?
Merge integrates an entire branch and records the relationship. Cherry-pick copies one commit's diff as a brand-new commit with a different SHA — useful for backporting a hotfix, but it duplicates work if the source branch is merged later.
What causes a non-fast-forward push rejection?
The remote branch has commits your local branch doesn't, so your push would discard them. Fix by fetching and then rebasing or merging, never by forcing.
A..B vs A...B?
In git log, A..B is commits reachable from B but not A; A...B is the symmetric difference (in either but not both). In git diff, A...B means "changes on B since it diverged from A" — the diff a pull request shows.
What does git stash actually store?
Hidden commits holding your modified tracked files (and, with -u, untracked ones), on a stack. Because they're commits, a dropped stash can still be found with git fsck --unreachable.
Squash merge — pros and cons?
Pro: one clean commit per feature on main, easy to read and revert. Con: you lose the individual commits, which hurts git bisect granularity and blame precision, and the source branch's SHAs never appear on main.
How does git bisect work?
Binary search over history. You mark a known-good and known-bad commit; Git checks out midpoints for you to test, halving the range each time, until it names the first bad commit. git bisect run <cmd> automates it entirely.
Lightweight vs annotated tag?
A lightweight tag is just a named pointer to a commit. An annotated tag is a full object with tagger, date, message, and optional GPG signature — use annotated for releases, since git describe and most tooling expect them.
What is origin/main, really?
A local, read-only cache of where main was on the remote the last time you fetched. It is not live. That's why git status can say "up to date" about a branch that moved ten minutes ago.
How do you resolve a merge conflict?
Run git status to list unmerged paths, edit each file to the correct combined result and remove the conflict markers, git add each resolved file, then git commit (merge) or git rebase --continue (rebase) — and run the tests. git merge --abort backs out entirely.
Git Survival Guide · Recovery-first reference. Rule of thumb: anything committed is recoverable via git reflog for ~90 days; anything uncommitted is not. Commit or stash before every destructive command.
